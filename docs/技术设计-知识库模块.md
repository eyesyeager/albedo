# Albedo · 知识库模块技术设计（实现级）

> 版本：v2.0
> 日期：2026-10-10
> 技术栈：Java 17 + Spring Boot 3.x + Spring AI 1.x（`Document` / `VectorStore` / `EmbeddingModel` / `TokenTextSplitter`）+ Apache Tika / PDFBox / Apache POI + 用户自配置向量库（Milvus / Qdrant / pgvector / Elasticsearch）与 Elasticsearch
> 关联需求：PRD v0.3 §6.4 知识库管理、§6.3 模型管理（Embedding/Reranker 接入）、§7 非功能需求、§8 技术架构、§9 核心数据模型
> 上下游模块：依赖「模型网关」（Embedding/Reranker 统一抽象）；向上为「智能体模块」提供检索能力（统一抽象为「工具」）
>
> **关键前提**：知识库模块**不内置向量数据库与 Elasticsearch 实例**，仅提供检索技术能力。向量库与 Elasticsearch 连接信息由用户在管理界面「检索引擎配置」中自行接入（预置主流向量库：Milvus / Qdrant / pgvector / Elasticsearch，支持自定义兼容服务）。

---

## 1. 模块概述

知识库模块提供**企业级文档理解与检索（RAG）**能力，是智能体「知识助手/智能客服」场景的基础。多库联合检索作为知识库的**内置能力**，不单独暴露「检索服务」实体（PRD 修订 v0.3）。

### 1.1 定位

- **文档接入**：10+ 类型文档上传、OCR/图文混排/表格/公式解析、大文件支持（≥ 200MB）。
- **索引构建**：切片、向量化（绑定 Embedding 模型）、增量同步、索引重建。
- **检索能力**：向量检索、混合检索（BM25 + 向量，RRF 融合）、Reranker 重排、多轮改写、标签过滤、来源溯源、多库联合检索。
- **检索引擎外接**：向量数据库与 Elasticsearch 均为**用户自配置**，平台仅提供接入能力与检索链路，不内置实例。
- **调试能力**：知识库内检索测试，可视化查看召回结果与分数。

### 1.2 职责边界

| 职责 | 说明 | 不包含 |
|------|------|--------|
| 知识库 CRUD | 创建/编辑/删除，绑定 Embedding/Reranker 模型 | 模型接入（模型网关） |
| 文档解析/切片/向量化 | 解析 → 切片 → 向量化 → 入库 | 模型推理本身 |
| 检索与重排 | 向量/混合检索、Reranker 重排、改写、过滤、溯源 | 智能体调度逻辑 |
| 检索测试 | 知识库内可视化召回测试 | 线上会话 trace |

### 1.3 术语约定

沿用 PRD §5：**知识库**是文档/数据集合，提供检索能力；**Chunk** 是切片后最小检索单元（含向量）；**Reranker** 来自模型管理中用户接入的模型，平台不内置。

本文在实现层新增下列与 Spring AI 对齐的术语：

| 术语 | 说明 |
|------|------|
| `Document` | Spring AI 文档抽象，承载 `content` + `metadata`（来源/页码/标签），切片、向量化、入库、召回全链路统一使用 |
| `VectorStore` | Spring AI 向量存储抽象，屏蔽具体向量库差异（Milvus/Qdrant/ES/pgvector 可替换） |
| `EmbeddingModel` | Spring AI 向量化抽象，由模型网关适配用户接入的 Embedding 服务后注入 |
| `TextSplitter` | Spring AI 切片抽象（`TokenTextSplitter` / 自定义标题层级切分） |
| `Parser` | 自定义文档解析器抽象，按文件类型插件化注册 |

### 4.2 核心组件职责（映射到 Spring AI）

| 组件 | 职责 | Spring AI / 技术落点 |
|------|------|----------------------|
| 知识库管理（KB Mgmt） | 知识库 CRUD、绑定 Embedding/Reranker/向量库/ES、切片策略配置 | 领域服务 + `KnowledgeBase` 表 |
| 检索引擎配置（Store Config） | 向量库 / Elasticsearch 连接信息维护、连通性测试 | 管理侧接口 + `VectorStoreConfig` / `ElasticsearchConfig` 表 |
| 文档管理（Doc Mgmt） | 上传/删除、状态机、标签、增量同步 | 领域服务 + `document` 表 |
| 解析服务（Parser） | 多格式解析 + OCR + 版面分析 | `DocumentParser` 插件 + Apache Tika/PDFBox/POI |
| 索引管线（Indexing） | 切片 → 向量化 → 入库，幂等可重试 | `TokenTextSplitter` + `EmbeddingModel` + `VectorStore` |
| 检索服务（Retriever） | 向量/混合检索、重排、改写、过滤、溯源、多库联合 | `VectorStore.similaritySearch` + 自研混合/重排层 |
| 重排适配层 | 统一 Reranker 调用（`query + documents[] → {index, score}`） | 自研 `RerankerClient`（经模型网关归一化） |

### 4.3 关键设计决策

| 决策 | 方案 | 理由 |
|------|------|------|
| RAG 全链路用 Spring AI 抽象 | `Document`/`VectorStore`/`EmbeddingModel`/`TextSplitter` 贯穿解析→切片→向量化→检索 | 对齐平台技术栈，向量库/Embedding 可替换 |
| 检索实现统一抽象 | 知识库在智能体侧抽象为「工具」，但检索实现内部独立服务 | 能力复用 + 边界清晰 |
| 解析异步化 | 大文档解析走消息队列异步任务，`parse_status` 状态机 | 200MB 文档不阻塞 |
| 向量库独立 | 向量存向量库，Chunk 元数据存 MySQL，原始文件存对象存储 | 解耦、可替换向量库 |
| 检索引擎外接 | 向量库与 ES 均由用户自配置，平台只注入 `VectorStore`（经连接信息初始化） | 平台不承担基础设施运维，适配私有化/多云形态 |
| 重排不走 Spring AI `DocumentRanker` | 自研 `RerankerClient`，统一 `query + documents[] → {index, score}`，经模型网关归一化 | Spring AI 0.8 已移除 `DocumentRanker`；对齐 rerank-接入方案 |
| 混合检索同源 | Elasticsearch 由用户自配置；若向量库选择 ES，则 BM25 + 向量同源，`VectorStore` 接口隔离 | 单引擎降低复杂度，支持 RRF 原生融合 |
| 增量同步 | 文档增删改触发索引增量重建，删除先于重建 | KB-13 |

## 5. 文档解析管线（实现级）

### 5.1 解析器注册表与插件化

解析器按文件类型插件化注册，新增格式只需实现 `DocumentParser` 并注册：

```java
public interface DocumentParser {
    Set<String> supportedTypes();   // 支持的文件扩展名 / MIME 类型
    List<Document> parse(InputStream in, String fileName, Map<String, Object> opts);
}
```

```java
@Service
public class ParserRegistry {
    private final Map<String, DocumentParser> parsers;

    // 构造时注入所有 DocumentParser 实现，按 supportedTypes 建立索引
    public DocumentParser resolve(String fileName) {
        String ext = extensionOf(fileName);
        return parsers.entrySet().stream()
            .filter(e -> e.getValue().supportedTypes().contains(ext))
            .map(Map.Entry::getValue)
            .findFirst()
            .orElse(tikaFallbackParser);
    }
}
```

### 5.2 PDF 解析（版面分析 + OCR 兜底）

PDF 优先走**文字层**（`PagePdfDocumentReader` 按页读，自动携带页码元数据），检测到扫描件（页面文字占比低）时**降级 OCR**：

```java
// 文字层优先：按页读取，保留页码元数据
PagePdfDocumentReader reader = new PagePdfDocumentReader(
    resource,
    PdfDocumentReaderConfig.builder()
        .withPageTopMargin(0).withPageBottomMargin(0)
        .build());

List<Document> pages = reader.get();
for (Document page : pages) {
    if (page.getText().length() < SCAN_THRESHOLD) {   // 疑似扫描页
        page.getMetadata().put("needs_ocr", true);    // 标记，后续 OCR 兜底
    }
}
```

OCR 与版面分析在异步解析任务中执行，图片文本**并入同页 Chunk**（图文混排），并保留公式/表格结构信息。

### 5.3 解析产物约定

解析产物统一为 `List<Document>`，每条携带标准元数据（供切片/过滤/溯源复用）：

| 元数据键 | 说明 |
|----------|------|
| `kb_id` / `doc_id` | 归属知识库/文档 |
| `file_name` / `page` | 来源文件、页码 |
| `heading` | 所属标题层级 |
| `tags` | 文件标签（检索过滤） |

## 6. 切片与向量化（实现级）

### 6.1 切片器

按 `split_mode` 选择切片器：`fixed`/`by_paragraph` 用 `TokenTextSplitter` 滑动窗口；`by_heading` 先按标题层级切段，再对超长段用 `TokenTextSplitter` 二次切分：

```java
TokenTextSplitter splitter = TokenTextSplitter.builder()
    .withDefaultChunkSize(kb.chunkSize())          // 512 tokens
    .withMinChunkSizeChars(100)                    // 最小字符数，避免碎块
    .withMinChunkLengthToEmbed(10)                 // 过短片段不参与向量化
    .withMaxNumChunks(10000)                       // 单文档块数上限
    .withKeepSeparator(true)                       // 保留分隔符语义
    .build();

List<Document> chunks = splitter.apply(documents); // 输入已携带来源元数据
```

### 6.2 向量化（`EmbeddingModel` 批处理）

向量化走**批处理**（单次请求传入 `List<String>`），显著降低大文档索引时的调用开销：

```java
List<String> texts = chunks.stream().map(Document::getText).toList();

// 模型网关注入的 EmbeddingModel，批处理返回对应顺序的向量
EmbeddingResponse response = embeddingModel.embedForResponse(texts);

for (int i = 0; i < chunks.size(); i++) {
    Embedding emb = response.getResults().get(i).getOutput();
    chunks.get(i).getMetadata().put("embedding", emb);   // 向量回写 Document
}
```

### 6.3 维度一致性约束

知识库**锁定 Embedding 模型**（`embedding_model_id`）。切换模型时维度可能变化，需**重建索引**并提示（风险 §15）。向量维度可通过 `embeddingModel.dimensions()` 在知识库创建时校验。

## 7. 索引写入（VectorStore）

### 7.0 检索引擎外接（用户自配置）

知识库模块**不内置向量数据库与 Elasticsearch 实例**，二者均由用户在管理界面「检索引擎配置」中自行接入：

- **向量数据库**：预置主流向量库（Milvus / Qdrant / pgvector / Elasticsearch，支持自定义兼容服务），填写连接信息（地址 / 端口 / 库名 / 集合 / 鉴权 / 向量维度）后做连通性测试；
- **Elasticsearch**：混合检索的关键词（BM25）召回依赖 ES，填写 Endpoint / 用户名 / 密码 / 索引前缀后做连通性测试。

运行时由 `VectorStore` 工厂根据用户配置的连接信息初始化对应实现，业务代码通过 `VectorStore` 接口隔离选型差异、零感知。混合检索的关键词召回在「向量库选择 ES」时复用同一索引，其余方案回退到 MySQL FULLTEXT / Redis 倒排。

### 7.1 向量库选型（预置）

| 方案 | 优势 | 适用 |
|------|------|------|
| Elasticsearch | BM25 + dense_vector 同源，RRF 原生融合，元数据过滤强 | 混合检索优先，单引擎降低复杂度 |
| Milvus | 纯向量性能强，海量向量扩展好 | 纯向量检索、超大知识库 |
| Qdrant | 轻量高性能，过滤表达式丰富 | 中小规模、云原生部署 |
| pgvector | 与业务库同源，运维成本低 | 中小规模、强一致诉求 |

### 7.2 写入与删除

```java
vectorStore.add(chunks);                 // 切片向量化后批量写入

// 删除：先删向量，再删元数据（增量同步一致性，§9）
vectorStore.delete(chunkIds);            // chunk.id 作为向量主键，与 MySQL 对齐
```

## 8. 检索实现

### 8.1 向量检索

```java
SearchRequest request = SearchRequest.builder()
    .query(query)
    .topK(topK)
    .similarityThreshold(0.5)                                   // 相似度阈值
    .filterExpression(FilterExpressionBuilder.builder()
        .eq("kb_id", kbId)
        .in("tags", tagFilter)                                  // 标签过滤（KB-10）
        .build())
    .build();

List<Document> hits = vectorStore.similaritySearch(request);
```

### 8.2 混合检索（KB-07）：RRF 融合

向量检索与关键词检索（BM25）并行召回，用 **Reciprocal Rank Fusion（RRF）** 归一化融合，避免两类分数尺度不一致：

```
RRF_score(d) = Σ 1 / (k + rank_d)      // k 默认 60
```

```java
List<Document> vecHits = vectorSearch(query, topK);
List<Document> bm25Hits = keywordSearch(query, topK);   // ES BM25 / MySQL FULLTEXT

Map<String, Double> fused = rrf(vecHits, bm25Hits);     // 按 chunk_id 合并 RRF 分数
List<Document> candidates = sortByScoreDesc(fused);
```

### 8.3 重排适配（RerankerClient）

自研统一语义接口，屏蔽厂商字段差异（`rerank-接入方案`）。实际推理经**模型网关**归一化：

```java
public interface RerankerClient {
    // query + documents[] → 按相关性降序的 { index, score }
    List<RankedDoc> rerank(String query, List<String> documents, int topN);
}

record RankedDoc(int index, double score) {}
```

```java
// 检索主链路中：召回候选 → 重排 → 截断 topK
List<RankedDoc> ranked = rerankerClient.rerank(query, candidateTexts, topK);
List<ChunkHit> finalHits = pickByIndex(candidates, ranked);
```

### 8.4 多轮改写（KB-09）

改写由知识库服务承担，运行时把「历史对话摘要 + 当前 query」作为上下文，调用模型网关生成检索 Query。智能体侧只透传 `knowledge.rewrite` 开关（见智能体模块 §7.3）。

### 8.5 多库联合检索（KB-08）

```java
// 对每个挂载知识库并行召回 → 合并候选（去重/按 kb 权重）→ 统一重排 → 截断
List<Document> merged = kbIds.stream()
    .parallel()
    .flatMap(kbId -> retrieveSingle(kbId, query, config).stream())
    .toList();
```

多库联合检索在知识库服务内部完成合并，智能体侧无感知。

### 8.6 来源溯源（KB-11）

每个召回 Chunk 携带 `source`（`kb_id`/`doc_id`/`file_name`/`page`），供前端角标引用与原文跳转；检索响应统一返回 `chunks` + `sources`。

## 9. 增量同步与索引构建

### 9.1 增量同步（KB-13）

```
文档增删改 → 记录 index_task（type=index/delete）
  → 异步消费：删旧向量（vectorStore.delete）→ 重新切片向量化 → 写入
  → 失败进入重试队列（retry_count++），告警
```

### 9.2 索引重建（Embedding 切换）

切换 `embedding_model_id` 触发全库重建：逐文档重跑解析/切片/向量化管线，新索引就绪后**原子切换**，避免检索期间混用旧维度向量。

### 9.3 幂等与一致性

- `index_task` 以 `document_id + type` 幂等，重复投递不重复建索引；
- 删除遵循「**先删向量，再删元数据**」，避免检索到已删除文档的脏数据；
- 任务重试采用指数退避 + 死信队列，最终一致性校验（比对 `doc_count`/`char_count`）。

## 10. 关键流程

### 10.1 文档接入（上传 → 索引）

```
上传文档 → 对象存储（原始文件，oss_key）
  → 写 document 记录（parse_status=pending）
  → 投递解析任务（消息队列）
  → Parser 解析（OCR/版面/表格/公式）→ List<Document>（含来源元数据）
  → Indexing：TokenTextSplitter 切片 → EmbeddingModel 批处理向量化
  → VectorStore.add → 写 chunk 元数据（MySQL）
  → 更新 parse_status=success（失败=failed，可重试）
  → 更新 KB doc_count/char_count
```

### 10.2 检索主链路（供智能体调用）

```
query + 检索配置（rewrite/tagFilter/topK/multiKB/rerank）
  → [可选] 多轮改写（结合上下文生成检索 Query）
  → 多库召回：每库执行向量检索（或混合检索 RRF 融合）
  → 合并候选 + 标签过滤
  → [可选] Reranker 重排（RerankerClient 经模型网关）
  → 截取 topK → 返回 { chunks, sources }（含原文/来源角标）
```

### 12.1 数据库表

## 14. 非功能性要求

### 14.1 性能

| 指标 | 目标 |
|------|------|
| 检索延迟 | < 500ms（P95，含重排） |
| 200MB 文档解析 | 可解析，异步不阻塞 |
| 文档索引吞吐 | 水平扩展，队列削峰 |
| 检索测试响应 | P95 < 800ms（含可视化） |
| Embedding 批处理 | 单文档切片一次性批处理，减少调用次数 |

### 14.2 安全

- 资源按 owner_uid 严格隔离，检索/文档操作强制校验归属；
- 文档内容安全审核（上传时），敏感文件访问控制；
- API Key 不落明文（模型网关统一密文管理）；
- 解析产生的临时文件及时清理。

### 14.3 可扩展性

- 向量库可替换（`VectorStore` 抽象存储接口）；
- 解析器插件化（`DocumentParser` 按文件类型注册），新增格式易扩展；
- 重排适配层支持任意 OpenAI 兼容 `/rerank` 服务（`RerankerClient` 统一语义）。

### 14.4 可观测性

- 索引任务全量状态可追踪（`index_task`），失败告警；
- 检索链路埋点（召回数/重排耗时/来源命中）；
- 全链路 trace_id。

## 15. 潜在风险与应对措施

| 风险 | 影响 | 应对 |
|------|------|------|
| 文档解析准确率不足（OCR/表格/公式） | 检索效果差 | 版面分析 + OCR 兜底 + 人工纠偏入口（PRD §12.1） |
| 大文档解析耗时/失败 | 索引积压 | 异步队列 + 分片解析 + 重试/断点续传 |
| 向量库选型绑定 | 迁移成本高 | `VectorStore` 抽象接口，向量与元数据分离 |
| 用户未配置向量库/ES | 知识库无法索引/检索 | 创建知识库前强制校验；「检索引擎配置」提供连通性测试与缺失提示 |
| Reranker 厂商字段不统一 | 重排结果错误 | 模型网关归一化统一语义（对齐 rerank-接入方案） |
| Embedding 维度不一致 | 检索失败 | 知识库锁定 Embedding 模型，切换需重建索引并提示 |
| 增量同步数据不一致 | 检索脏数据 | 删除先于重建、幂等任务、最终一致性校验 |

## 16. 与其他模块衔接

- **模型网关**：知识库仅持有 `embedding_model_id` / `reranker_model_id`，实际推理经网关注入的 `EmbeddingModel` / `RerankerClient`。
- **智能体模块**：将知识库检索抽象为「工具」（`@Tool` 方法内调用 `knowledgeService.retrieve`），智能体下发 `query + 检索配置`，接收召回 + 来源（用于角标溯源）。
- 多库联合检索由知识库服务内部合并多库召回结果后统一返回，智能体侧无感知。
