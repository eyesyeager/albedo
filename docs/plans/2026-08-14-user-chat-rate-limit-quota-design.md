# Albedo 用户维度对话限流与日限额设计探索

**日期**：2026-08-14  
**状态**：已收敛，作为 PRD V1.4 输入  
**需求来源**：@Boss「每用户默认 QPM=3、每日默认 50 次、租户独立、前端展示每日额度」

## 1. 现状与问题

现有消息限流已经按 `tenantId + uid` 隔离，在建立 SSE 前执行分钟固定窗口和小时固定窗口检查；分钟、小时窗口纪元均为 UTC。阈值来自平台作用域 `sys_config`，当前为 30 次/分钟、120 次/小时。该配置模型不能表达租户级覆盖，也没有日限额、日用量或剩余额度的数据来源。前端已能消费 `10005 + retryAfterSeconds`，并在输入区展示倒计时。

本需求不是单纯修改两个阈值，而是新增两类业务能力：短时防突发的 QPM 限流，以及按租户日历日控制资源使用的每日限额。两者必须有不同的错误语义、恢复条件和前端状态，同时保持用户、租户、幂等与隐私边界。

## 2. 计数口径备选

### 方案 A：有效请求一进入就计数

优点是规则简单、并发控制直接；缺点是参数错误、配置错误、模型未启动等没有产生回答的请求也消耗日额度，用户难以接受。

### 方案 B：仅完整回答成功才计数

优点是最偏向用户；缺点是停止生成、SSE 断流和已产生部分内容的失败请求实际已消耗模型资源却不计数，容易被反复停止或断流规避额度。

### 方案 C：按“已开始的有效生成尝试”计数（推荐）

请求先完成身份、租户、参数、幂等、限流、限额及业务配置校验；在模型生成开始前预占一次资格。模型一旦开始产出助手内容、工具调用或其他可归属于本次回答的模型输出，即结算为一次。生成前失败释放预占；生成开始后的完成、停止、断流或失败均计一次。该方案以“是否已经消耗生成资源”为统一解释，兼顾用户公平、资源治理和并发精确性。

同一 `Idempotency-Key` 的网络重放只对应同一次尝试，不重复计数。用户主动发起“重试”或“重新生成”属于新的生成尝试；若新尝试开始生成则再次计数，但不得重复创建用户消息。

## 3. 限流、限额与时间边界备选

### 概念拆分

QPM 是短时防突发控制，命中后等待当前分钟窗结束即可继续，沿用 `10005 RATE_LIMITED` 与 `retryAfterSeconds`。每日限额是资源权益控制，命中后必须等到当前租户日历日结束，使用独立业务错误 `DAILY_QUOTA_EXHAUSTED`，返回重置时间与额度快照。复用 `10005` 会使前端把“等到明天”错误表现为秒级倒计时，因此否决。

现有 120 次/小时高于 50 次/日，永远不会先于日限额产生有效约束，且增加第三种恢复语义，因此废弃小时窗业务规则。QPM 保留固定分钟窗；分钟边界采用 UTC 不影响“一分钟”的用户理解。

### 日界线方案

- UTC 0 点：实现统一，但国内用户每天 08:00 重置，违背“今日”语义。
- 用户个人时区：更个性化，但项目没有用户时区来源，同租户报表和治理边界会分裂。
- 租户时区 0 点（推荐）：与既有“面向用户时间按租户时区展示”一致，同一租户口径统一。

租户时区直接使用现有租户必填 IANA `timezone`，不新增时区配置。一个额度日定义为租户当地 00:00 至下一当地 00:00；夏令时日允许为 23 或 25 小时。接口返回 UTC 绝对时间及租户时区，前端按租户时区显示“明日 00:00 重置”。

## 4. 配置分层备选

- 每租户必须显式配置：隔离最直观，但新租户漏配即不可用，且无法统一调整缺省策略。
- 仅平台配置：与“每租户独立额度”冲突。
- 平台数据库默认 + 租户覆盖（推荐）：默认 QPM=3、日限额=50，租户可分别覆盖；默认值与覆盖值都来自数据库，代码没有业务阈值常量。

配置语义包含：QPM 是否启用及阈值、日限额是否启用及阈值、生效时间、配置作用域与版本/更新时间。平台默认缺失或非法时不得用代码值兜底；租户覆盖缺失时继承平台默认，覆盖存在但非法时不得静默回退。配置变更只影响生效后的新尝试，不追溯修改已结算用量；当日下调到低于已用量时立即视为用尽，上调后按新总量恢复可用。

一期不做用户级白名单或单独加额。原始需求只要求租户独立，引入个人权益会新增授权、到期、冲突优先级和申诉语义。配置模型只定义平台与租户作用域，不为想象中的用户覆盖预留空字段；未来有明确权益场景时新增独立需求。

## 5. 前端信息架构与同步

每日额度与“能否发送”直接相关，放在首页和会话详情共用的 Composer 状态区域，靠近输入与发送操作；不放顶栏、侧边栏或用户菜单，避免信息与动作分离。产品要求呈现：今日剩余次数、已用/总量、下一次重置时间；具体排版、尺寸与视觉层级由 @UI 决定。

登录后进入对话页时，通过新的当前用户额度查询接口获取权威快照。生成开始并完成一次结算时，沿用当前发送响应通道下发更新后的额度快照；每日限额拒绝响应携带同形快照。页面恢复、跨标签页回到前台或状态不确定时重新查询校准，不以前端本地自减作为最终事实。

日额度用尽后保留输入能力和草稿，禁用发送操作并持续传达重置时间；用户仍可编辑、复制文本和停止正在进行的生成。QPM 命中时同样只临时禁用发送，倒计时结束恢复，不自动发送。匿名用户不请求、不展示个人额度，发送仍走现有 SSO。

额度属于受保护的个人运行数据。查询与发送响应只按可信 Host 建立的当前租户及当前登录 uid 返回，不接受客户端传入 uid/tenantId，不允许跨租户缓存或聚合返回。

## 6. 观测、异常与验收方向

普通计数、QPM 命中和日额度命中属于高频运行事件，不新增逐次安全审计 action；应形成不含消息正文的运行指标/用量记录。配置变更属于治理动作，进入产品化配置入口时必须审计；当前直接改库阶段沿用受控 DBA 变更流程，不编造尚不存在的管理入口。

关键验收覆盖：第 4 次分钟请求触发 QPM；第 51 次日尝试触发每日限额；同一 uid 在 gift/redbook 独立；租户当地跨日重置；生成前失败不计、生成后停止/断流/失败计；相同幂等键不重复计，主动重试/重新生成按新生成尝试计；前端初始展示、实时更新、跨标签页校准和用尽禁发均准确。

## 7. 按价值裁剪的一期不做项

1. **用户级白名单/加额**：原始场景没有个人权益管理诉求，会引入新的授权和公平性规则。
2. **小时限流**：在 50 次/日约束下无独立业务价值，且造成多余恢复语义。
3. **额度购买、套餐、结转、赠送**：属于商业化权益系统，不属于资源治理型限额。
4. **未用额度跨日结转**：与“每日额度”口径冲突，会使总量和重置语义复杂化。
5. **租户管理员查看单个用户额度/用量页面**：本需求只要求终端用户查看本人额度；管理后台当前 Deferred，且个人用量查询涉及额外权限和隐私目的。
6. **每次命中写安全审计**：限流/限额不是安全管理动作，高频审计会混淆安全审计语义；保留脱敏运行观测即可。
