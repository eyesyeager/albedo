## 1. 模块概述

智能体模块是 Albedo 的核心模块，承载「应用（Application）」的**全生命周期管理**与**运行时执行**，对外以 **AGUI 协议**提供标准 Agent 能力。

### 1.1 定位

- **管理侧**：应用的创建、智能体配置、调试、启用/停用、历史快照回滚。
- **运行时侧**：承载单智能体的「规划—执行—反思」循环（ReAct），统一调度知识库检索与 MCP 工具调用。
- **对外侧**：通过 AGUI 协议事件流（SSE）向任意前端/业务系统暴露 Agent 能力，与前端解耦。

### 1.2 边界与职责

| 职责 | 说明 | 不包含 |
|------|------|--------|
| 应用 CRUD 与配置 | 基础信息、模型选择、Prompt、工具装配、轮次/记忆/检索配置 | 模型本身的接入（模型网关） |
| 配置快照与回滚 | 每次保存自动生成快照，支持历史对比与一键回滚 | 灰度发布（已删除） |
| 智能体运行时 | ReAct 循环、工具调度、轮次控制、流式输出 | MCP 协议适配（MCP 网关）、检索实现（知识库服务） |
| AGUI 协议服务 | 会话、消息、中断、事件流、JWT 验签、QPM 限流 | JWT 签发（业务方自签） |
| 会话记录与 Trace | 消息落库、工具调用轨迹、链路回放 | 操作审计日志（独立模块） |

### 1.3 术语约定

沿用 PRD §5：**应用**是可发布智能体单元（保存即生效，可启用/停用）；**智能体**是具备规划、工具调用、记忆能力的 LLM 应用实例；**工具**是统一抽象的能力单元（含 MCP 工具、Skill 模板）；**AGUI** 是 Agent 与前端/业务系统的标准交互协议（事件流）。

本文在实现层新增下列与 Spring AI 对齐的术语：

| 术语 | 说明 |
|------|------|
| `ChatClient` | Spring AI 对话客户端，链式装配 Prompt / 工具 / Advisor |
| `ToolCallback` | Spring AI 工具统一抽象（`@Tool` 方法、MCP 工具均归一化为它） |
| `ToolCallingManager` | Spring AI 工具调用管理器，驱动「模型输出工具请求 → 执行 → 回灌」循环 |
| `ReactAgent` | Spring AI Alibaba 的 ReAct 智能体封装（内置自动上下文工程、HITL） |
| `StateGraph` | Spring AI Alibaba Graph 状态图，多智能体编排的运行时基座 |

### 2.1 配置模型（`config_json`）

应用配置统一序列化为 `config_json`，字段如下（与前端 `AppConfig` 对齐）：

```jsonc
{
  "model": "model_id",            // 绑定 LLM 模型 id
  "modelMode": "fixed",           // fixed=固定模型 | auto=智能模式（AUTO/性能/均衡/经济）
  "prompt": "系统提示词",
  "reactRounds": 5,               // 1–50，默认 5
  "shortMemory": 5,               // 短期记忆轮数 0–30，默认 5
  "knowledgeStrategy": "smart",   // smart=智能调用 | always=必定调用
  "knowledge": {                  // APP-18 检索配置
    "rewrite": true,              // 多轮改写
    "tagFilter": ["标签A"],        // 标签过滤
    "showSource": true,           // 来源展示
    "recallTopK": 5               // 召回数量
  },
  "tools": [                      // 工具装配（ToolBinding）
    { "kind": "KnowledgeBase", "id": "kb_id", "enabled": true, "strategy": "smart" },
    { "kind": "MCP", "id": "mcp_id", "enabled": true, "strategy": "smart", "disabledTools": ["danger_tool"] }
  ],
  "envVars": { "SOME_SECRET": "encrypted_value" }  // APP-16 环境变量/鉴权
}
```

### 2.2 智能模式（LLM 路由，MD-03）

`modelMode = auto` 时按任务复杂度动态路由到四档模型（AUTO/性能/均衡/经济），由模型网关完成实际路由，智能体模块仅下发「档位」意图。

### 4.2 运行时核心组件（映射到 Spring AI）

| 组件 | 职责 | Spring AI 落点 |
|------|------|----------------|
| **Planner（规划器）** | 基于 Prompt + 历史消息 + 工具描述，产出工具调用意图 | 由 `ChatModel` 生成 function-call 请求，`ToolCallingManager` 解析 |
| **Executor（执行器）** | 执行工具调用（委托 MCP 网关/知识库服务），收集结果 | `ToolCallingManager` 调用 `ToolCallback.call(toolInput, toolContext)` |
| **Reflector（反思器）** | 结合工具结果评估是否继续、是否给最终答案 | 工具结果回灌消息列表后，由模型下一轮自主判断（ReAct 收敛） |
| **ToolScheduler（调度器）** | 维护工具注册表、按 `strategy`/`disabledTools` 过滤、校验轮次 | 运行时装配 `List<ToolCallback>` + 自定义 `ToolCallingManager` 包装 |
| **EventEmitter（事件流）** | 将运行过程转成 AGUI 事件经 SSE 推送 | `ToolCallback` 装饰器 + `Flux` 流映射（§5.4） |
| **MemoryStore（短期记忆）** | 按 `shortMemory` 轮数截取上下文窗口 | `MessageWindowChatMemory` + Redis `ChatMemoryRepository` |
| **SessionService（会话服务）** | 会话创建/消息落库/中断；以 `app_id + session_id` 隔离 | 自研领域服务 |

### 4.3 关键设计决策

| 决策 | 方案 | 理由 |
|------|------|------|
| 主运行时用 `ChatClient` 而非直接 `ReactAgent.call` | 对外 AGUI 需要 token 级流式 + 工具调用细粒度事件，`ChatClient` 底层可控；`ReactAgent` 用于子 Agent/节点 | 事件粒度可控 |
| 工具统一抽象为 `ToolCallback` | 知识库、MCP、Skill 在运行时全部归一化为 `ToolCallback` 注入 `ChatClient` | 对齐 Spring AI 原生模型，复用 `ToolCallingManager` |
| 会话匿名 | 不维护 user_id，以 `app_id + session_id` 隔离 | PRD 修订 v0.3 |
| 保存即生效 | 无独立发布态；回滚也是保存即生效 | 简化生命周期 |
| 快照回滚 | 每次保存写入 `AppConfigSnapshot`，回滚 = 取快照重写当前配置 | 保留历史、可对比 |
| 流式输出 | SSE + AGUI 事件，token 级推送 | 首字延迟 < 1s 目标 |
| 多 Agent 编排预留 | MVP 单 Agent；架构预留 `StateGraph` + `TaskToolsBuilder.subAgent` | PRD 范围「多智能体后续」，但技术底座先行 |

## 5. Agent 实现

### 5.1 单智能体的两种形态

| 形态 | 实现 | 适用场景 |
|------|------|----------|
| **主运行时** | `ChatClient` + `ToolCallingManager` + `ChatMemory` + 自研 `AgentRuntime` | 对外 AGUI（需 token 级流式 + 事件） |
| **子 Agent / 图节点** | `ReactAgent.builder()` | 多 Agent 编排、内部委托（§8） |

### 5.2 主运行时：ChatClient 装配

```java
ChatClient chatClient = ChatClient.builder(chatModel)          // 模型网关适配后的 ChatModel
    .defaultSystem(config.prompt())                            // APP-11 系统提示词
    .defaultTools(assembleToolCallbacks(appId, config))        // §6 装配的工具
    .defaultAdvisors(MessageChatMemoryAdvisor
        .builder(shortMemory(appId, config))                   // §7 短期记忆
        .build())
    .build();
```

> 说明：`chatModel` 不是直接 new 的模型客户端，而是「模型网关」暴露的统一 `ChatModel` 实现（内部按 `modelMode` 做智能路由）。智能体模块对模型客户端零依赖。

### 5.3 ReAct 循环协议（模型 ↔ ToolCallingManager）

Spring AI Alibaba 的 ReAct 循环**不写在业务代码里**，而是 `ToolCallingManager` 与模型之间的交互协议，循环体等价于：

```
1. 组装 messages = [System] + 历史(短期记忆) + [User 新消息]
2. chatModel.call(messages, tools)  →  返回 AssistantMessage
   ├─ 含 toolCalls → emit TOOL_CALL_START/ARGS
   │     对每个 toolCall：
   │       ① ToolScheduler 过滤（disabledTools/strategy）
   │       ② toolCallback.call(input, toolContext) → ToolResult
   │       ③ 结果 append 为 ToolResponseMessage 回灌 messages
   │       ④ emit TOOL_CALL_END + 写 ToolCallTrace
   │     本轮轮次 +1，若 < reactRounds 则回到 step 2（否则强制收敛）
   └─ 无 toolCalls → 得到最终答案，循环结束
```

实现上通过「包装 `ToolCallingManager` + 自定义 `ToolCallback` 装饰器」在①②③④处埋点，把内部过程转换为 AGUI 事件（§5.4）。轮次控制（`reactRounds`）在包装层做计数与强制截断：

```java
// 轮次控制伪代码：包装 ToolCallingManager，超过 reactRounds 后禁止再发起工具调用
class BoundedToolCallingManager implements ToolCallingManager {
    private final int maxRounds;
    private final AtomicInteger round = new AtomicInteger(0);

    public ToolCallingChatOptions executeToolCalls(...) {
        if (round.incrementAndGet() > maxRounds) {
            return ToolCallingChatOptions.builder()
                .toolCallAllowed(false)          // 禁止再调工具，强制模型输出最终答案
                .build();
        }
        return delegate.executeToolCalls(...);
    }
}
```

### 5.4 流式输出与 AGUI 事件映射

对外 SSE 链路用 `Flux` 把 `ChatClient.stream()` 的 token 流与工具调用拦截映射为 AGUI 事件：

| AGUI 事件 | 来源 |
|-----------|------|
| `RUN_STARTED` / `RUN_FINISHED` / `RUN_ERROR` | `AgentRuntime` 调用前后、异常捕获 |
| `TEXT_MESSAGE_START` / `_CONTENT` / `_END` | `chatClient.prompt().stream().content()` 的 `Flux<String>` 逐 token 映射 |
| `TOOL_CALL_START` / `_ARGS` / `_END` | `ToolCallback` 装饰器在 `call()` 前后埋点 |
| `STATE_SNAPSHOT` / `STATE_DELTA` | 轮次/工具进度状态变更时由 `AgentRuntime` 推送 |
| `STEP_STARTED` / `STEP_FINISHED` | 每个 ReAct 轮次边界 |

```java
// 工具装饰器：在 ToolCallback 外层包一层，负责发事件 + 落 trace
class TracingToolCallback implements ToolCallback {
    private final ToolCallback delegate;
    public String call(String toolInput, ToolContext ctx) {
        emit(TOOL_CALL_START, name(), toolInput);
        try {
            String out = delegate.call(toolInput, ctx);
            trace.record(name(), toolInput, out, OK, latency);
            emit(TOOL_CALL_END, name(), out);
            return out;
        } catch (Exception e) {
            trace.record(name(), toolInput, null, ERROR, latency);
            emit(TOOL_CALL_END, name(), e);
            throw e;
        }
    }
    public ToolDefinition getToolDefinition() { return delegate.getToolDefinition(); }
}
```

### 5.5 中断与取消

`interrupt` 请求写 Redis `run:cancel:{session_id}` 标志；`AgentRuntime` 在**每个 ReAct 轮次边界**与**每个 token 发射前**检查该标志，命中则：
- 停止继续调用 LLM/工具（对 `Flux` 调用 `cancel()` 触发下游断开）；
- 抛出自定义 `RunInterruptedException`，映射为 `RUN_ERROR`/中断事件；
- 会话状态置 `interrupted`。

## 6. 工具 / Skill / MCP 装载

### 6.1 工具统一抽象

知识库检索、MCP 工具、Skill 模板在运行时**全部归一化为 `ToolCallback`**，由 `ToolScheduler` 统一装配进 `ChatClient`：

```java
List<ToolCallback> assembleToolCallbacks(Long appId, AgentConfig config) {
    List<ToolCallback> callbacks = new ArrayList<>();
    for (ToolBinding b : config.tools()) {
        if (!b.enabled()) continue;
        switch (b.kind()) {
            case KnowledgeBase -> callbacks.add(knowledgeTool(appId, b));  // 知识库检索工具
            case MCP           -> callbacks.addAll(mcpTools(appId, b));    // MCP 工具列表
            case Skill         -> skillIds.add(b.refId());                 // Skill 不产出工具，收集为上下文（§6.3）
        }
    }
    // 全局过滤 disabledTools + 包 TracingToolCallback 装饰器
    return callbacks.stream()
        .filter(c -> !b.disabledTools().contains(c.getToolDefinition().name()))
        .map(TracingToolCallback::new)
        .toList();
}
```

**本地工具**（平台内置能力，非 MCP）用 `@Tool` 注解声明，例如知识库检索工具：

```java
class KnowledgeRetrievalTool {
    @Tool(name = "retrieve_knowledge",
          description = "检索企业知识库，返回带来源的文档片段。适合回答需要内部资料的问题。")
    public String retrieve(
        @ToolParam(description = "检索查询词") String query,
        @ToolParam(description = "目标知识库 id 列表") List<String> kbIds,
        ToolContext toolContext) {
        // 经知识库服务检索，附多轮改写/标签过滤/topK 配置
        RetrieveResult r = knowledgeService.retrieve(kbIds, query, config);
        return Json.toJson(r);       // 归一化为字符串返回给模型
    }
}
```

### 6.2 MCP 装载

MCP 工具由「MCP 网关」完成协议适配（`initialize`/`tools/list`/`tools/call`），智能体运行时通过 `ToolCallbackProvider` 将网关产出的工具描述转换为 `ToolCallback`：

```java
// 运行时按 app 挂载的 mcp_id 向 MCP 网关拉取工具，构造 ToolCallback
List<ToolCallback> mcpTools(Long appId, ToolBinding binding) {
    List<ToolDef> defs = mcpGateway.listTools(appId, binding.refId()); // 已过滤禁用
    return defs.stream()
        .map(d -> MethodToolCallback.builder()
            .method("callMcp", McpInvoker.class)         // 内部统一转发方法
            .name(d.name())
            .description(d.description())
            .inputSchema(d.inputSchema())                // 透传 JSON Schema
            .build())
        .toList();
}

class McpInvoker {
    // 统一转发：实际 tools/call 在 MCP 网关执行，密钥由网关解密注入
    public String callMcp(String args, ToolContext ctx) {
        return mcpGateway.callTool(appId, mcpId, ctx.getName(), args);
    }
}
```

> 直接接入自建 MCP（不走网关场景）也可用 `SyncMcpToolCallbackProvider` 将 `McpSyncClient` 的会话工具批量暴露为 `ToolCallback`；本期统一走 MCP 网关以复用工具级禁用与鉴权注入能力。

### 6.3 Skill 装载（上下文注入，不是工具）

> **重要变更**：Skill 与 MCP **完全隔离**。Skill **不再**是「MCP 封装模板」，而是一份独立的**指令与资料包**（文件夹），**不绑定、不依赖、不产出 MCP 工具**。详见《技术设计-Skill模块》§1、§5.7。

装载链路：

```
Skill（入口 Markdown 指令 + 参考文档 + 可选资源）
  → SkillResolver.resolve(appId, skillIds)
  → ① 入口正文（去 frontmatter）→ 拼入系统提示的「技能指令」段
  → ② 参考资料 → 先给「路径 + 摘要」清单，模型显式请求时再取全文（按需加载）
  → 不产出任何 ToolCallback，不经过 MCP 网关
```

**与 MCP 的分工**：

| | MCP | Skill |
|---|---|---|
| 运行时形态 | `ToolCallback`（可调用工具） | 上下文文本（指令 + 资料） |
| 作用位置 | 模型发起 `tool_call` | 系统提示 / 上下文 |
| 相互依赖 | 无 | 无（删除/故障互不影响） |

装配阶段对 `ToolBinding.kind = Skill` 的分支**不再**调用 `mcpTools`/`skillTools`，改为收集 `skillIds` 交由 `SkillResolver` 生成上下文。

### 6.4 per-app 工具过滤与策略

| 维度 | 实现点 |
|------|--------|
| 工具级禁用 | `ToolAppBinding.enabled=false` 的工具在装配阶段过滤掉（§6.1） |
| 智能/必定调用 | `strategy=always` 的工具强制参与每一轮（`ToolCallingChatOptions.toolCallAllowed=true` + 限定候选集）；`smart` 交由模型判断 |
| 轮次校验 | `BoundedToolCallingManager` 计数（§5.3） |
| 工具描述注入 | 工具 `description` + `inputSchema` 由装配时注入运行时，供模型规划 |

## 7. 上下文优化

### 7.1 短期记忆（`shortMemory` 轮数）

使用 `MessageWindowChatMemory` 按「消息数」截断上下文窗口，存储走 Redis 实现（保证多实例一致）：

```java
ChatMemory shortMemory(Long appId, AgentConfig config) {
    return MessageWindowChatMemory.builder()
        .chatMemoryRepository(redisChatMemoryRepository)   // Redis，key 前缀含 app_id+session_id
        .maxMessages(config.shortMemory() * 2)             // 一轮 = user + assistant 两条消息
        .build();
}
```

- `shortMemory = 0` → 不注入历史，仅保留系统提示词 + 当前消息；
- 记忆按 `app_id + session_id` 隔离，TTL 与会话一致；
- 通过 `MessageChatMemoryAdvisor` 自动装配进 `ChatClient`，无需手动拼历史。

### 7.2 Token 级窗口与自动上下文工程

- `MessageWindowChatMemory` 按消息数截断，但单条消息可能超长（如大段文档召回）。**补充 Token 预算约束**：在组装 messages 后估算 token，超过模型上下文上限时按「保留 System → 优先截断最早的中间历史 → 保护最近一轮」策略裁剪，必要时截断单条长消息。
- Spring AI Alibaba Agent Framework 内置**自动上下文工程**：在 `ReactAgent` 形态下自动裁剪/压缩上下文；主运行时（`ChatClient`）侧由自研 `TokenBudgetAdvisor` 兜底。

```java
// Token 预算裁剪 Advisor（示意）
class TokenBudgetAdvisor implements CallAdvisor {
    private final int maxTokens;   // 来自模型网关下发的上下文长度
    public AdvisedRequest adviseRequest(AdvisedRequest req, ...) {
        List<Message> trimmed = trimByTokenBudget(req.messages(), maxTokens);
        return req.withMessages(trimmed);
    }
}
```

### 7.3 多轮改写（KB-09 / APP-18）

知识检索的多轮改写由**知识库服务**承担（智能体模块只下发 `query + 检索配置`）。运行时在「必定调用知识库」或模型主动触发检索工具时，把「历史对话摘要 + 当前 query」作为检索上下文传入，由知识库服务生成改写 Query。智能体侧只负责：维护短历史供改写使用、透传 `knowledge.rewrite` 开关。

### 7.4 长期记忆（预留）

PRD 将长期记忆列为后续迭代。架构预留：
- 会话匿名（无 user_id）限制跨会话记忆，预留 `Conversation` 增加 `user` 标识的扩展点；
- 长期记忆可接入 Spring AI Alibaba 的 **Mem0** 聊天记忆（持久化 + 语义检索），通过替换 `ChatMemory` 实现即可，不动运行时主链路。

## 8. 多 Agent 调度（预留，技术底座先行）

> MVP 为单智能体；多智能体协作在 PRD 列为后续迭代（APP-32「发布为组件」即其基础）。本节给出基于 Spring AI Alibaba Graph 的既定实现路径，供后续直接启用。

### 8.1 子 Agent 作为工具（TaskToolsBuilder.subAgent）

最轻量的多 Agent 形态：把子 Agent 注册为可被主 Agent 调用的「工具」：

```java
@Bean("salesAgent")
public ReactAgent salesAgent(ChatModel chatModel) {
    return ReactAgent.builder()
        .name("sales-agent")
        .description("负责售前咨询与报价的专家")
        .model(chatModel)
        .systemPrompt(SALES_PROMPT)
        .tools(salesTools)                 // 子 Agent 自己的工具
        .build();
}

// 主 Agent 通过 TaskToolsBuilder 将子 Agent 注册为工具
TaskToolsBuilder taskTools = TaskToolsBuilder.builder()
    .subAgent("sales-agent", salesAgent)   // API 方式注册
    .build();
List<ToolCallback> mainTools = taskTools.getToolCallbacks();
```

- 主 Agent 规划阶段看到「sales-agent」工具，按需把子任务委托给它；
- `TodoListInterceptor` 可注入任务规划工具（`write_todos`）+ 规划提示词，支撑多步任务拆解。

### 8.2 StateGraph 编排

复杂编排用 `StateGraph` 构建有向图，`ReactAgent` 作为图节点：

```java
StateGraph graph = new StateGraph("workflow", new OverAllState());
graph.addNode("router", routingAgent);      // 路由/分类节点
graph.addNode("sales", salesAgent);         // ReactAgent 节点
graph.addNode("support", supportAgent);
graph.addEdge(START, "router");
graph.addConditionalEdges("router",
    state -> "sales".equals(state.value("active_agent")) ? "sales" : "support",
    Map.of("sales", "sales", "support", "support"));
graph.addEdge("sales", END);
graph.addEdge("support", END);
CompiledGraph compiled = graph.compile();
```

`OverAllState` 为共享状态，支持 `KeyStrategy`（如 `ReplaceStrategy`）定义字段合并规则，供跨节点传递上下文。

### 8.3 Handoffs 路由

多专家「转交」模式：每个 Agent 暴露 handoff 工具，通过更新共享状态实现节点间路由：

```java
@Tool(name = "transfer_to_support", description = "转交给售后支持专家")
public String transferToSupport(
        @ToolParam(description = "转交原因") String reason,
        ToolContext toolContext) {
    ToolContextHelper.getStateForUpdate(toolContext)
        .ifPresent(u -> u.put("active_agent", "support"));   // 更新路由状态
    return "已转交售后支持";
}
```

父图用条件边读取 `active_agent` 完成路由（§8.2 的 `addConditionalEdges`）。工具内读写状态统一走 `ToolContextHelper.getState / getStateForUpdate`。

### 8.4 Routing 模式

「先路由再执行」模式：`LlmRoutingAgent` 依据用户意图分发到目标专家，`RoutingMergeNode` 合并各分支结果，适合明确的意图分类场景。与 Handoffs 的区别在于路由决策发生在**入口**而非对话中途。

### 8.5 与主运行时的关系

- 主运行时（AGUI）在 MVP 阶段直接挂单 `ReactAgent`/`ChatClient`；
- 多 Agent 场景下，AGUI 事件流仍以「主 Agent 的视角」输出，子 Agent 的调用通过 §8.1 的 Task 工具抽象为一次 `TOOL_CALL_*` 事件，前端无感知；
- `StateGraph` 编排可作为 `AgentRuntime` 的一种实现替换，对外协议不变。

## 9. 关键流程

### 9.1 应用保存（含快照生成）

```
用户编辑配置 → PUT /v1/apps/{id}
  → 校验配置（模型存在、工具可挂载、轮次范围）
  → 序列化 config_json
  → 更新 Application 记录
  → 写入 AppConfigSnapshot（diff 对比，无变化则跳过）
  → 若启用态：刷新运行时缓存（Redis 缓存新配置 + 重建工具装配）
  → 返回 { app, snapshot_id }
```

### 9.2 对外对话（AGUI 主链路，实现级）

```
业务方自签 JWT → POST /agui/apps/{app_id}/chat（SSE）
  → Gateway：JWT 验签（HS256，可选 exp）→ QPM 限流 → 应用启用校验
  → AgentRuntime：
      · 创建/复用 session
      · 组装上下文：System(Prompt) + ChatMemory(短期记忆) + 工具描述
      · emit RUN_STARTED
  → ReAct 循环（≤ reactRounds 轮，BoundedToolCallingManager 控制）：
      chatModel.call(messages, toolCallbacks)
      ├─ 产出 toolCalls → emit STEP_STARTED
      │     ToolScheduler 过滤 → TracingToolCallback.call(...)
      │       → emit TOOL_CALL_START/ARGS/END + 写 ToolCallTrace
      │     结果回灌 messages → 下一轮
      └─ 产出最终文本 → emit TEXT_MESSAGE_START/CONTENT/END（token 流）
  → 消息与工具调用按 trace_id 关联落库（幂等）
  → emit RUN_FINISHED → 关闭 SSE
```

### 9.3 会话中断

```
POST /agui/apps/{app_id}/sessions/{sid}/interrupt
  → Redis 写 run:cancel:{session_id}
  → AgentRuntime 在轮次边界 / token 发射前检查 → 中断 Flux + 停止 LLM/工具
  → emit RUN_ERROR/中断事件 → 会话标记 interrupted
```

### 9.4 调试台

复用运行时链路，但：不落线上会话（或标记 `is_debug`），额外透出 token 明细、检索结果、完整入参返回（APP-22），事件流通过管理侧鉴权通道推送。

### 9.5 快照回滚

```
POST /v1/apps/{id}/rollback  { snapshot_id }
  → 读快照 config → 写回 Application.config_json
  → 生成新快照（记录「回滚自 snapshot_id」）
  → 刷新运行时缓存（保存即生效）
```

## 10. 接口定义

### 10.1 对外运行时接口（AGUI，JWT 验签 + QPM 限流）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/agui/apps/{app_id}/sessions` | 创建会话，返回 `session_id` |
| POST | `/agui/apps/{app_id}/chat` | 发起对话（SSE 事件流） |
| GET | `/agui/apps/{app_id}/sessions/{sid}/messages` | 历史消息 |
| POST | `/agui/apps/{app_id}/sessions/{sid}/interrupt` | 中断运行 |

**JWT 验签约定**（PRD §10.1）：HS256；业务方用应用 Jwt Key 自签，平台仅验签；不强校验 claim，若携带 `exp` 则校验过期；每应用独立 Jwt Key，支持新旧 Key 过渡。

**AGUI 事件清单**（对齐 PRD §10.1，映射关系见 §5.4）：

| 事件 | 说明 |
|------|------|
| RUN_STARTED / RUN_FINISHED / RUN_ERROR | 运行生命周期 |
| TEXT_MESSAGE_START / TEXT_MESSAGE_CONTENT / TEXT_MESSAGE_END | 文本流 |
| TOOL_CALL_START / TOOL_CALL_ARGS / TOOL_CALL_END | 工具调用 |
| STATE_SNAPSHOT / STATE_DELTA | 状态同步（APP-38） |
| STEP_STARTED / STEP_FINISHED | 规划步骤 |

### 10.2 管理侧接口（RESTful，`@Permission(USER)`）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/v1/apps` | 创建应用 |
| GET | `/v1/apps/{id}` | 查询详情 |
| PUT | `/v1/apps/{id}` | 更新（保存即生效） |
| POST | `/v1/apps/{id}/enable` `/disable` | 启用/停用 |
| POST | `/v1/apps/{id}/rollback` | 回滚到历史快照 |
| GET | `/v1/apps/{id}/snapshots` | 快照列表/对比 |
| POST | `/v1/apps/{id}/debug/chat` | 调试台对话（SSE） |
| GET | `/v1/apps/{id}/sessions` | 会话列表 |
| GET | `/v1/sessions/{sid}/trace` | 运行链路回放 |

### 10.3 统一约定

- 对外鉴权 `Authorization: Bearer <JWT>`；管理侧 `authorization` Header（eyesUser token）。
- 错误码统一 `{ code, message, request_id }`；限流错误码统一约定。
- 全链路携带 `trace_id`。

## 13. 非功能性要求

### 13.1 性能

| 指标 | 目标 |
|------|------|
| 流式首字延迟（平台侧开销） | < 1s（不含模型推理） |
| ReAct 单轮调度开销 | < 200ms |
| 工具装配（含 schema 拉取） | 缓存命中 < 20ms |
| 会话回放加载 | 按 session 分页，P95 < 300ms |
| 配置保存 | < 200ms（含快照生成） |

### 13.2 安全

- 对外 API JWT 验签（HS256），Jwt Key 密文存储，支持 Key 轮换过渡；
- 管理侧 eyesUser 鉴权，资源按 owner_uid 强隔离（无跨用户共享）；
- MCP 密钥/环境变量加密存储、运行时注入，禁硬编码；
- 输入/输出内容安全审核（拦截违规，RUN_ERROR 返回）；
- 传输全程 HTTPS/TLS。

### 13.3 可用性与可扩展性

- 无状态运行时可水平扩展；会话上下文与记忆存 Redis 保证多实例一致；
- 模型不可用时优雅降级（切换到备用模型档位）；
- 核心服务 99.9% 可用，会话/消息/轨迹数据备份。

### 13.4 可观测性

- 全链路 trace_id 贯穿（Gateway → Runtime → 模型/工具）；
- 结构化日志、指标（调用量/Token/错误率）、告警；
- 会话与工具调用 trace 回放（OBS-03）。

## 14. 潜在风险与应对措施

| 风险 | 影响 | 应对 |
|------|------|------|
| ReAct 死循环/超长链路 | 成本失控、超时 | `BoundedToolCallingManager` 轮次上限 + 单轮超时 + 全局超时熔断 |
| Token 超限（长历史/大召回） | 上下文溢出、成本高 | `TokenBudgetAdvisor` 裁剪 + 窗口截断 + 自动上下文工程 |
| JWT Key 泄露 | 外部滥用 | 每应用独立 Key + 多版本轮换 + QPM 限流 + 异常监控 |
| 流式 SSE 连接中断 | 体验差、状态不一致 | 断线重连 + STATE_SNAPSHOT 状态同步 + 幂等落库 |
| 会话匿名导致长期记忆受限 | 后续迭代受限 | 预留 user 标识扩展点 + Mem0 接入方案，MVP 明示范围 |
| 工具 schema 变更/高危工具 | 调用错误、安全风险 | 装配时校验 + `disabledTools` 过滤 + 调用审计 |
| AGUI 版本不对齐 | 前端不兼容 | 事件子集与协议版本对齐，预留适配层 |
| 模型不可用 | 运行失败 | 备用模型降级 + 明确错误事件 + 健康检查 |
| QPM 默认值未定 | 限流不合理 | 提供默认值并按应用可配置 |
| 多 Agent 编排提前落地风险 | 复杂度/稳定性 | MVP 仅单 Agent；Graph 底座预留，启用需评审 |

## 15. 与其他模块衔接

- **模型网关**：向智能体模块注入统一 `ChatModel`（含流式）与上下文长度；智能体模块只传模型 id / 档位。
- **知识库服务**：作为一类「工具」挂载，智能体模块下发 `query + 检索配置`，接收召回结果 + 来源（用于角标溯源）。
- **MCP 网关**：提供工具列表与统一调用入口（schema → `ToolCallback`）；智能体模块负责 `disabledTools` 过滤、`TracingToolCallback` 埋点与轮次控制。
- 衔接统一以 `trace_id` 贯穿，保证会话回放完整还原链路。
