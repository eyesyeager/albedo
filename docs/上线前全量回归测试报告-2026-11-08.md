## 6. 缺陷清单

### P0-1（阻塞，已修复）Skill L3 日志类型越界，导致日志页 / 工作区快照 500

**现象**
1. Skill 运行 `run_q7syt3wj` 完成 L3 资源读取后，`GET /api/v1/logs`（默认首页）返回 `Internal Server Error`；日志页显示「共 0 条记录」「没有找到匹配的日志」，所有类型计数为 0。
2. `GET /api/v1/workspace/bootstrap` 同时返回 500；`main.tsx` 启动快照、`api.auth.login()` 内的 `replaceFromServer()` 均失败 → 重新登录时出现错误 Toast，前端只能依赖残留内存状态进入概览。
3. `GET /api/v1/logs?...&runId=run_q7syt3wj` **永久 500**，即该次 Skill 运行的执行链路永远无法查看。
4. 连带影响：设置页「保存策略」后出现 `请求失败（500）` Toast；浏览器 console 出现 15 次 500。
5. 该缺陷有「时间窗」特征：当更新的日志把坏行挤出首页 / 快照窗口后，日志页与 bootstrap 会自行恢复 200（本次约 10 分钟后恢复），但 `runId` 链路仍永久失败。

**根因**
- `backend/app/runtime/tools.py:75` 定义 L3 工具 `kind="skill_resource"`；`backend/app/runtime/engine.py:765` 直接以 `log_type=event["kind"]` 写日志。
- `backend/app/schemas/domain.py:9` 的 `LogType = Literal["session","mcp","skill","tool","model","system"]` 未包含 `skill_resource` / `skill_script`。
- `backend/app/api/v1/logs.py:134-175` 的 `query_logs(response_model=PageResult)` 序列化时抛 `ResponseValidationError` → 500；`LogDetail` 同理。
- 证据：导出文件 `backend/var/exports/exp-xqelcc.json` 共 3018 条，`type` 分布中出现 `skill_resource: 1`；后端日志堆栈 `Input should be 'session','mcp','skill','tool','model' or 'system', input: 'skill_resource'`。

**修复方案（已实施，采用「归一化 + 别名兼容」，对外契约不变，前端无需改动、无需数据迁移）**
- `backend/app/schemas/domain.py`：新增 `LOG_TYPES`、`LOG_TYPE_ALIASES`（`skill_resource` / `skill_script` → `skill`）、`normalize_log_type()`、`log_type_values()`。
- `backend/app/services/audit.py`：`make_log_entry()` 在写入前统一归一化 type，所有日志写入路径（engine / audit / MCP / 模型透传）一处收口，杜绝新增越界类型。
- `backend/app/services/snapshot.py`：新增 `log_dict()`，读取日志行时兼容历史脏数据；`build_workspace()` 的日志快照改用它。
- `backend/app/api/v1/logs.py`：分页、导出、详情与执行链路改用 `log_dict()`；`typeCounts` 合并别名；`type` 筛选同时匹配规范类型与历史别名。
- `backend/app/api/v1/stats.py`：概览类型计数同样合并别名，与日志页口径一致。
- `backend/tests/test_governance.py`：新增 2 条回归用例（写入归一化纯函数；注入历史 `skill_resource` 行后验证日志页 / 筛选 / 链路 / 快照 / 概览全部 200）。

分层级别、动作与资源路径仍由 `skill_load_records` 与日志 `name` / `summary` 保留，可观测性不下降。

### P2-1 概览「较昨日」变化率文案出现 `+-x%`，且箭头方向固定

**现象**：概览「今日调用」显示 `↗ 较昨日 +-94.7%`（后续 `+-92.1%`）。
**根因**：`frontend/src/pages/OverviewPage.tsx:79` 硬编码 `+${formatPercent(...)}`，而 `frontend/src/lib/format.ts:78-80` 对负值已经返回 `-94.7%`；同时 `↗` 不随正负变化。
**建议**：改为按符号选择 `+/-` 与 `↗/↘`，例如 `sub={`${delta >= 0 ? '↗' : '↘'} 较昨日 ${delta >= 0 ? '+' : ''}${formatPercent(delta)}`}`。

### P3-1 保存模型配置后连接状态被重置为「未测试」，发布按钮随即禁用

**现象**：在模型详情抽屉仅修改备注并「保存更改」后，抽屉头部从「连接正常」变为「未测试」，`发布新版本` 按钮置灰（`title=需启用并通过连接测试`），必须重新点「测试」才能发布。
**根因**：`ModelDetailDrawer.tsx:34` / `ModelRow.tsx:29` 的 `canPublish` 依赖 `connection === 'normal'`，而 PATCH 模型配置会清空该状态。
**建议**：区分「Base URL / 上游 Key 变更」（需要重测）与「备注等不影响连接的字段」（保留 `normal`），或在保存后自动触发一次连接测试。

### 观察项（非缺陷，但需在发布说明中明确）

1. **推理型模型 + 小 `max_tokens`**：`chat/completions` 传 `max_tokens=32` 时返回 `content=""`、`reasoning_content` 有内容、`finish_reason=length`（上游把预算全部用于思考）；提高到 512 后正常返回「回归通过」。属上游行为，建议示例文档提高默认 `max_tokens`。
2. **错误模型标识的状态码分场景**：不存在的标识返回 404 `model_not_found`；存在但不属于当前 Key 返回 403 `model_not_allowed`。历史 E2E 用例用不存在的标识期望 403，属用例设计偏差，非产品缺陷（本次两种场景均已验证）。
3. `GET /api/v1/logs/exports` 返回 404：该列表端点不存在，前端按 `taskId` 轮询 `GET /api/v1/logs/exports/{id}`，实际导出与下载均正常，不影响功能。
